# 每日比赛：报名、共享分队与赛果

路由 `/arena/events`，也可在 `/arena` 的“每日比赛”页签进入。2026-10-16 实现。沿用现有 Next Node 服务、附件持久化目录及镜像部署；不修改 Docker、Compose 或 Nginx。

## 身份

报名身份和浏览选手分开。仍有有效营地会话的旧用户可直接获得本站报名凭证，无须额外扫码。旧档案若没有角色指纹，首次报名会通过该用户的有效营地会话补齐一次。

报名凭证是有效期 30 天的本站 HMAC 签名 Cookie（HttpOnly、SameSite=Lax，HTTPS 时 Secure），只含选手 ID 与过期时间。签名密钥保存在现有 Arena 数据目录的 `.identity-key`，32 随机字节、权限 0600；原子建立，多个进程使用同一份密钥。它不是 QQ、微信或营地访问令牌，不允许据此读取营地战绩或修改游戏档案偏好。退出登录会同时清除本机的报名凭证。切换浏览其他选手不会切换报名身份。

匿名访客可以查看公开报名、分队和赛果；修改报名需服务端验证的身份，不能在请求体传一个公开 playerId 冒充他人。唯一性单位是游戏选手账号，无法仅凭这套登录判断不同 QQ/微信账号是否属于同一真人。

## 每日状态与并发

- 北京时间（Asia/Shanghai）划分日期，无需部署额外定时任务。每天独立报名，跨日不会把昨天的报名自动带到今天。
- 一份日期 JSON 保存参赛/观战报名、每场固定名单、分路、算法版本、评分快照、核验过程与赛果。文件在 `arenaDataDirectory()/.events/YYYY-MM-DD.json`。
- 文件写入使用日期锁和临时文件原子替换。并发请求在同一份文件上顺序修改；第十人到齐只创建一场，重复报名不增加人数。
- 分队只在服务端修改事务中生成，seed、名单、结果一起落盘。GET 不重新随机。前端每约四秒拉取共享状态，同一修订版本的结果完全相同。
- 观战不计入十人。当前场次锁定后，切观战/退出只影响下一场，已排定的十人快照不被重写。
- 昨天尚未核验的场次可以补核验和记录，但不会再为历史日期自动创建下一场。

## 超过十人的安排

按用户确认的规则：当天已排入场次数少者优先；再按最近排入的场次、报名时间、固定 ID 顺序排序，选前十人。其余参赛报名保留为候补，观战席不进入候选。退出再报名会重新排队。

选定十人后复用现有五路模型与公平分队算法。团队均值差、平均对位差、最大对位差、分路偏好和证据差决定原始公平目标；最近三场仅影响公平候选中的抽样权重：

`H = 0.08 × 队内重复队友累计 + 0.06 × 重复分路累计`，历史按 `0.6^场次距离` 衰减。

候选抽样权重 `exp(-2 × (H_A + H_B))`。历史项不能改变原始最优参考，也不能放宽原有四个公平阈值、解除硬约束。新场次使用新 seed，不承诺每场一定换队。未建立正式校准的胜率模型，不因单场胜负大改五路评分，也不以跨位置 KDA 自动惩罚游走。

研究参考：[Microsoft PlayFab：规则权重](https://learn.microsoft.com/en-us/xbox/playfab/multiplayer/matchmaking/rule-weights)。其说明区分资格硬限制和候选排序权重。本实现据此保留硬限制与公平候选范围，再作轻量历史抽样；并未接入 PlayFab 服务或声称实现 TrueSkill。

## “比赛已结束”的流程

1. 本场任一参赛选手点击核验。观战者不能用不在场的账号读取一场本人并未参加的游戏。
2. 检查营地临时授权和报名身份是否一致；失效返回明确的重新扫码提示。本站 30 天报名凭证不能替代营地授权。
3. 后台读取点击者的本人个人页及最新战绩页，只检查本场生成后出现、且不在赛前已导入记录中的最近三个候选。
4. 详情读取限定为本人最新战绩页返回的 gameSeq、gameSvr、relaySvr、battleType 完整元组和个人页验证过的角色。没有客户端指定任意地址/目标账号/对局的入口。
5. 单场必须完整返回两边各五人、十个不同角色指纹；与赛前十人完全一致，且两边阵营与分队一致（蓝/红可整体互换）。昵称相同、九人相同、缺角色或阵营不同都不能自动记胜负。本人角色、可用时的本人英雄和胜负也会核对。
6. 唯一匹配时记录赛果、生成数据分析，并在同一日期文件事务中安排下一场。多场匹配时保留已核验候选，让本场选手选择实际那场；前端不能上传自编的胜负或统计。
7. 来源指纹在 `.events/verified/` 留收据，同一营地对局不能重复计为其他场次。重复点击、并发核验或陈旧异步结果不能重复开下一场。

核验是后台任务，HTTP 发起后立即返回，前端读取共享进度。服务重启中断任务时，超过两分钟可手动重新核验。上游隐私限制、限流、网络失败、最新页尚无记录或缺字段时，保留当前场次，既不猜胜负也不提前开下一场。重新扫码只能刷新授权，不能保证解除上游的数据缺失或隐私限制。

接口合同来自原项目作者的[固定 camp-api.ts](https://github.com/lizupingsama/Honor-of-Kings-Match-Dashboard/blob/c04acbabe21c85230c5911a07c6aba55577ea634/src/lib/camp/camp-api.ts)和[camp-client.ts](https://github.com/lizupingsama/Honor-of-Kings-Match-Dashboard/blob/c04acbabe21c85230c5911a07c6aba55577ea634/src/lib/camp/camp-client.ts)。这是作者代码的一手实现证据，不是腾讯公开 API 保证。沿用项目已有的 Mulan PSL v2 适配及许可声明。

## 记录与导出

每场保留双方名单、分路安排、赛前分数、算法版本、胜负、营地对局标识、战绩时间、核验者与时间；个人英雄、K/D/A、营地评分、经济、输出、承伤、参团率在上游返回时保存。

当日统计只累计核验通过的场次，含参赛、胜负、累计 KDA、已返回评分的均值和有效统计样本数。缺失值保留为空，不冒充零。日期选择器可查看历史，`GET /api/arena/events/export?date=YYYY-MM-DD` 导出当日 JSON 记录供内部奖励结算；本站不定义或发放奖励。

## 验证与实际边界

已用当前本人 QQ 会话读取最近一场，确认实际返回 `blueRoles/redRoles` 的十人角色面板，以及 killCnt/deadCnt/assistCnt、gradeGame、money、输出、承伤和 joinGamePercent 等字段。连接检查只返回字段结构与可用性，不保存或公开那场其他玩家的原始身份和面板。

多人报名到下一场的状态推进用隔离临时目录与虚构十人对局验证，涵盖并发双实例、重复报名、候补轮换、阵营互换、错人/错队/旧记录拒绝、多候选确认、重启恢复、陈旧任务、跨日和来源防重复。当前共 40 项测试及生产构建通过。

另启动独立的生产服务进程，确认没有原营地会话时仍能通过已签名报名凭证认出本人，并在已有角色指纹的情况下修改报名席位；两个进程读取同一份报名文件。真实本人报名、切换观战、退出报名、手机 390px 无页面溢出、桌面 1440px 分队、历史日期切换、赛后明细与 JSON 导出已检查。真实数据目录的测试报名已退出，虚构比赛仅保存在隔离临时目录。

还没有十位真实参与者在新报名系统中实际打完一场，因此真实自定义房间的赛后核验仍需在首场活动中确认。

现有部署为单机持久化目录。日期锁支持共享同一文件系统的服务进程，不声称支持文件不共享的多节点部署。比赛房间仍需在游戏内自行建立。
